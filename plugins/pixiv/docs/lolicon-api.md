# Lolicon API 调研

官方文档：<https://docs.api.lolicon.app/#/setu>（markdown 源：`https://docs.api.lolicon.app/setu.md`）。
除特别注明外，结论均为 2026-10-13 ～ 2026-10-15 期间直接调用接口实测得到。

## 结论速览

- **随机图 API，没有分页**，不能按 pid 取，也没有排序。
- 请求里**只要带 `Referer` 或 `Origin` 就返回 403**。
- `r18=0`（非 R18）**不保证全年龄**：库内分类与 pixiv 的 R-18 标记不一致。
- 有严格限流，形态有两种：HTTP 429，或 HTTP 200 加 `error` 字段。
- 图库从 pixiv 开站覆盖到前一天，几乎实时更新，规模远大于文档所说的「手工添加」。

## 接口

```http
GET  https://api.lolicon.app/setu/v2
POST https://api.lolicon.app/setu/v2   (Content-Type: application/json)
```

不需要 apikey。GET 用同名参数重复表示数组（`tag=a&tag=b`），POST 可直接传数组或二维数组。

### 请求参数

| 参数 | 类型 | 默认 | 说明 |
|------|------|------|------|
| `r18` | int | `0` | `0` 非 R18、`1` R18、`2` 混合；**库内分类**，不等于作品本身的 R-18 标记 |
| `num` | int | `1` | 1～20；条件太窄时返回更少 |
| `uid` | int[] | | 指定画师，最多 20 个 |
| `keyword` | string | | 标题/作者/标签模糊匹配，文档自己说性能和准度差，建议用 `tag` |
| `tag` | string[] | | 数组项之间 AND（最多 3），项内用 `\|` 分隔为 OR（最多 20）；标签与作者名按 2～3-gram 匹配，标题完全匹配，大小写不敏感 |
| `size` | string[] | `["original"]` | 返回哪些规格的地址：`original` / `regular` / `small` / `thumb` / `mini` |
| `proxy` | string | `i.pixiv.re` | 图片地址的反代域名，可用 `{{pid}}`、`{{path}}` 等占位符；传假值得到原始 `i.pximg.net` 地址 |
| `dateAfter` / `dateBefore` | int | | pixiv 上传时间（毫秒时间戳），含边界 |
| `dsc` | bool | `false` | 关闭缩写自动展开（如 `fgo`、`舰b`、`少前`） |
| `excludeAI` | bool | `false` | 排除 AI 作品 |
| `aspectRatio` | string | | 正则 `((gt\|gte\|lt\|lte\|eq)[\d.]+){1,2}`，如 `gt1` 横图、`lt1` 竖图、`gte1.777lte1.778` |

布尔假值：`0`、`false`、`null`、它们的字符串形式与空字符串，其余为真。

### 响应

`{ error: string, data: setu[] }`。`setu` 字段：`pid`、`p`（页号）、`uid`、`title`、`author`、`r18`、
`width`、`height`、`tags`（含中文翻译）、`ext`、`aiType`（`0` 未知、`1` 否、`2` 是）、`uploadDate`（毫秒）、
`urls`（按 `size` 给出的地址）。

同一作品的不同页是独立条目，可能在一次返回里同时出现（如 `150832283_p1` 与 `_p2`）。

文档另说明：两年内上传、且距上次更新超过 90 天的作品被取到时会进入后台更新队列，更新完成前返回的仍是旧信息。

## 实测发现

### 请求头：带 Referer / Origin 即 403

逐个请求头测试（`num=1`）：

| 请求头 | 结果 |
|--------|------|
| 无 | 200 |
| `Referer: https://www.pixiv.net/` | **403** |
| `Origin: https://www.pixiv.net` | **403** |
| `Referer: https://api.lolicon.app/`（它自己的域名） | **403** |
| `x-requested-with: XMLHttpRequest` | 200 |
| `Cookie: PHPSESSID=…`（有值） | 200 |
| `Referer`、`Origin`、`Cookie` 均为空值 | 200 |

只要 `Referer` 或 `Origin` 有值就拒绝，与取值是哪个域名无关；值为空则不受影响。所以调用方如果给请求
统一加了来源头（比如为访问 pixiv 设置的 `Referer: https://www.pixiv.net/` 与 `Origin`），请求这个接口前
必须把它们去掉或置空。`Cookie` 不影响结果，但同一套请求头里如果带着 pixiv 等站点的登录 Cookie，
也应一并清空，避免把登录态发给第三方。

### 限流

- 间隔约 1.5 秒的连续请求会频繁被拦，被拦时是 **HTTP 200**，`error` 为 `"请求的太快啦，休息一会吧"`，`data` 为空。
  不看 `error` 字段会误以为「没有符合条件的图」。
- 连续请求较多时还会直接返回 **HTTP 429**。
- 间隔 5 秒、被拦后退避 30 秒的连续请求没有再被拦。

### `r18=0` 仍会返回 R-18 作品

抽 2026-10-14（北京时间）一整天、`r18=0` 的 20 个作品，其中 3 个（pid 150847215、150842270、150849034）
在 pixiv 标签里带 `R-18`，但返回的 `r18` 字段为 `false`。另一次 `r18=0` 的 3 个结果里也有 1 个。

### 时间范围与规模

用「取本批最早（最晚）时间作为下一次的 `dateBefore`（`dateAfter`）」逐步逼近，每端 4～5 次请求收敛，
最后一次返回少于 `num`，说明窗口内已全部返回，边界是确切值：

| | 上传时间 | 作品 |
|---|---|---|
| 最早 | 2007-09-13 14:19 UTC | pid 431（pixiv 2007-09-10 开站）；早于 2008-09-17 的只有 3 个 |
| 最近（2026-10-15 测得） | 2026-10-14 23:52 UTC | pid 150868925 |

- 最新作品是前一天上传的，19:20～23:52 UTC 之间仍有新增，说明图库**持续、近实时地更新**。
- 密度：2023-07-05 15:00 UTC 起的 2 分钟窗口内有 16 个作品，粗算单日上万。文档里「库中的图片全是由本人
  凭着性趣亲手添加」的说法与现状不符，更像是自动入库。
- 文档内嵌的 MongoDB Charts（「目前可以透露的情报」）是前端渲染，拿不到数据。

### 能否遍历全库

接口本身只随机抽，但**命中数少于 `num` 时会一次返回全部命中**（2 分钟窗口返回 16 个，少于 20）。
所以把时间窗口二分到每段少于 20 个，理论上能列出某一段的全部库存。

全库遍历不现实：按上面的密度需要数百万次请求，在限流下要几个月；作者也明确表示「不接受任何索要数据库的请求」「别整天搁那爬虫爬来爬去的」。小范围是可行的，例如限定画师 UID 或很窄的日期区间。
按 `dateAfter` 追新时要注意它筛的是 pixiv 上传时间而不是入库时间，图库补收的老作品会被漏掉。

### 参数实测

- 标签 OR（`tag=原神|鸣潮`）、多画师（`uid=33217935&uid=4754550`）、`aspectRatio=gt1` / `lt1`、`r18=1`、
  `excludeAI` 均按文档生效。
- `tag=原神|鸣潮` 加 2026-10-14（JST）整天只命中 5 个，且全是竖图，再加 `aspectRatio=gt1` 就是 0 个。
  组合条件过窄时返回空是正常结果。
- 默认 `proxy` 的 `i.pixiv.re` 原图在国内可直连（HTTP 200、约 1MB）。

## 样本质量

2026-10-14（北京时间）全天、`r18=0`、原图，随机 20 个：

- 分辨率普遍很高，多数短边 ≥ 2000px，单张 0.8～14MB；最低是 1000×1415 与两张 1024×1536 的 AI 图。
- **竖图占 16/20**，横图只有 4 张。
- AI 作品 4 张（其中两张是同一作品的不同页）。
- 题材集中在热门手游与 VTuber（碧蓝档案、鸣潮、NIKKE、绝区零、原神、Hololive），偏色气向。
